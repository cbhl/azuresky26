# Small CLs

Source: https://google.github.io/eng-practices/review/developer/small-cls.html

## Why write small CLs

Small, simple CLs are:

- **Reviewed more quickly.** Five minutes several times is easier to find than a 30-minute block.
- **Reviewed more thoroughly.** Large changes lead to frustrating back-and-forth and missed points.
- **Less likely to introduce bugs.** Fewer changes are easier to reason about.
- **Less wasted work if rejected.** A rejected large CL wastes a lot of effort.
- **Easier to merge.** Long-lived large CLs accumulate conflicts.
- **Easier to design well.** Polishing a small change is easier than a large one.
- **Less blocking.** Self-contained pieces let you keep working while waiting for review.
- **Simpler to roll back.** Large CLs touch more files that change later.

Reviewers may reject a change outright for being too large. It is easier to write small CLs from the start than to split a large change afterwards.

## What is small

The right size is **one self-contained change**:

- Makes a minimal change that addresses just one thing (usually one part of a feature).
- Includes related test code.
- Everything the reviewer needs is in the CL, its description, the existing codebase, or a CL they have already reviewed.
- The system keeps working for users and developers after the CL is submitted.
- Is not so small that its implications are hard to understand. A new API should come with a usage of it in the same CL.

There are no hard rules. About 100 lines is usually reasonable; about 1000 lines is usually too large. The number of files also counts: 200 lines in one file may be fine, while 200 lines across 50 files usually is not. When in doubt, go smaller.

## When large CLs are acceptable

- Deleting an entire file counts as roughly one line of change.
- Changes generated by a trusted automatic refactoring tool, where the reviewer only verifies the intent. Merging and testing caveats still apply.

## Writing small CLs efficiently

Do not sit idle waiting for review. Work on several projects at once, find reviewers who are immediately available, do in-person or pair reviews, or split work so you can keep going.

## Splitting CLs

Plan how to split work into CLs before coding.

- **Stacking:** send one small CL for review, then start the next CL on top of it.
- **By files:** split by groups of files needing different reviewers, such as a proto change and the code that uses it, or a code change and its configuration/experiment.
- **Horizontally:** create shared code or stubs (for example a shared proto or API stub) to isolate layers so they can move independently.
- **Vertically:** split into small full-stack features that can proceed in parallel (for example, multiplication and division as separate features).
- **Combined:** chart a grid of layers by features, where each cell is a standalone CL.

## Separate refactorings

Put refactorings in a separate CL from feature changes or bug fixes. Small cleanups, such as renaming a local variable, can stay in the feature or fix CL.

## Keep related test code in the same CL

- Tests are expected for all changes.
- Logic changes need new or updated tests. Pure refactorings should be covered by tests too, adding them if missing.
- Independent test work can go in its own CL first: validating existing code, refactoring test code, or introducing larger test framework code.

## Do not break the build

If CLs depend on each other, make sure the system still works after each one is submitted.

## When the CL cannot be made smaller

This is very rare. Consider a refactoring-only CL first, ask teammates for smaller designs, and as a last resort get reviewers' consent in advance. Expect a long review, be vigilant about bugs, and write extra tests.
